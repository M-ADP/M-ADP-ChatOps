# ChatOps 대화형 UX 100% 설계

## 목적

이 문서는 현재 ChatOps의 사용자 경험을 기준으로, `사용자 UX 100%`에 도달하기 위해 무엇이 구현되었고 무엇을 더 해야 하는지를 정리한다.

여기서 말하는 100%는 다음을 의미한다.

- 사용자가 ChatOps를 API가 아니라 실제 LLM처럼 느낀다.
- 내부 상태, 내부 API 이름, 내부 ID를 보지 않고도 작업을 끝낼 수 있다.
- 자연어로 질문하고, 부족한 정보를 보완하고, 승인하고, 결과를 받는 흐름이 자연스럽다.
- 대화가 여러 턴에 걸쳐 이어져도 문맥이 안정적으로 유지된다.

## 현재 완료된 것

### 대화형 응답 계약

- `assistant_message` 중심 응답이 구현되어 있다.
- `input_required`는 사용자에게 자연어 질문으로 보인다.
- `pending_approval`는 자연어 계획 + 승인 질문으로 보인다.
- `completed`, `failed`는 사용자용 자연어 문구로 정리되어 있다.
- 내부 operation id와 내부 ID는 사용자 응답에서 노출하지 않는다.

### 대화형 정보 수집

- 부족한 값은 한 번에 모두 묻는다.
- 사용자가 여러 턴에 걸쳐 값을 보완하면 누적해서 수집한다.
- 프로젝트 생성은 핵심 파라미터 전체를 수집한 뒤에만 승인 단계로 간다.
- 애플리케이션 생성/수정/삭제도 중요 비즈니스 파라미터 기준으로 질문한다.

### 이름 + 문맥 기반 UX

- 사용자는 `project_id`, `application_id`를 몰라도 된다.
- 프로젝트와 애플리케이션은 이름 기준으로 해석한다.
- `그거`, `아까`, `방금` 같은 최근 문맥 표현을 일부 지원한다.
- 프로젝트 멤버 관련 명령은 `nickname` 기준으로 대상 사용자를 해석한다.

### 현재 사용자 입장에서 가능한 대화

- `demo 프로젝트 만들어줘`
- `그거 이름은 renamed-demo로 바꿔줘`
- `demo 프로젝트 멤버 목록 보여줘`
- `demo 프로젝트에 alice 멤버 추가해줘`
- `demo 프로젝트 api-demo 앱 만들어줘`
- `demo 프로젝트 api-demo 앱 로그 보여줘`

즉 조회/명령/승인 흐름의 기본 형태는 이미 대화형으로 작동한다.

## 아직 100%가 아닌 이유

### 승인 자체는 아직 API 동작에 의존함

현재는 사용자가 실제 채팅에서

- `응, 실행해`
- `아니 취소해`

처럼 말하는 대신, 내부적으로는 approve/reject API 호출이 필요하다.
즉 UX는 자연어 계획까지는 좋아졌지만, 승인 행위 자체는 아직 완전한 대화형이 아니다.

### 문맥 해석이 아직 제한적임

- `그거`, `아까 거`는 최근 문맥 중심으로만 동작한다.
- 더 긴 대화에서 어떤 대상을 가리키는지 안정적으로 추적하는 수준은 아니다.
- `방금 만든 앱`, `그 프로젝트의 다른 앱`, `첫 번째 멤버` 같은 표현은 아직 제한적이다.

### 자연어 표현 다양성 대응이 더 필요함

현재도 꽤 많은 표현을 처리하지만, 실제 사용자 표현은 더 다양하다.

예:
- `프로젝트 하나 파줘`
- `CPU는 하나 반 정도`
- `메모리는 1기가로`
- `아까 만든 거 지우고 다시 만들어`
- `그 사람 멤버 빼`

이런 표현까지 안정적으로 처리하려면 파라미터 추출과 문맥 해석을 더 고도화해야 한다.

### 질문과 결과 문구가 아직 더 다듬어져야 함

현재 문구는 충분히 읽히지만, 완전히 자연스러운 assistant 톤이라고 보기는 어렵다.
특히 다음이 더 필요하다.

- operation별 더 자연스러운 질문 문구
- 조회 응답의 가독성 정리
- 실패 메시지의 설명력 강화
- 다음 행동을 유도하는 짧은 후속 안내

### 다중 턴 값 수정/정정 UX가 부족함

예:
- `아니 CPU는 2로 해줘`
- `메모리는 1이 아니라 0.5야`
- `디스크는 20으로 바꿔`

이런 정정 흐름을 안정적으로 반영하는 UX는 아직 100% 수준이 아니다.

## 100% 도달을 위한 남은 작업

### 1. 승인/거절을 자연어 대화로 흡수

필수 작업:
- `응`, `실행해`, `진행해`, `취소해`, `아니` 같은 표현을 승인/거절 intent로 해석한다.
- 현재 `pending_approval` 요청이 있으면, 다음 사용자 발화를 승인/거절 또는 수정 요청으로 연결한다.
- approve/reject API는 내부 구현으로 남기되, 사용자에게는 숨긴다.

완료 기준:
- 사용자가 버튼 없이 자연어만으로 승인/거절할 수 있다.

### 2. 다중 턴 수정/정정 UX 추가

필수 작업:
- 이미 수집된 슬롯 값을 다시 덮어쓸 수 있어야 한다.
- 어떤 값이 현재 확정됐는지 내부 상태에 보관해야 한다.
- 사용자가 일부 값만 수정해도 승인 계획이 다시 생성되어야 한다.

완료 기준:
- 사용자가 이전에 준 값을 자연어로 정정할 수 있다.

### 3. 문맥 해석 고도화

필수 작업:
- 최근 1개 대상이 아니라 세션 문맥의 엔티티 집합을 관리한다.
- `그 프로젝트`, `그 앱`, `방금 만든 앱`, `그 사람` 같은 표현을 엔티티 타입별로 해석한다.
- project/application/user 참조를 혼동하지 않도록 entity memory를 분리한다.

완료 기준:
- 여러 턴 대화에서도 대상 해석이 안정적이다.

### 4. 자연어 파라미터 추출 강화

필수 작업:
- 구어체와 축약 표현을 더 많이 처리한다.
- 단위 표현을 정규화한다.
  - `1기가`, `1024`, `0.5GB`
  - `하나`, `1`, `한 개`
- 애매한 표현은 실행하지 않고 다시 묻는다.

완료 기준:
- 실제 사용자가 줄여 말해도 대부분 자연스럽게 해석된다.

### 5. 질문/결과 문구를 operation별로 다듬기

필수 작업:
- project/application/member/monitoring 별로 문구 템플릿 정리
- 질문 문구는 친절하지만 짧게 유지
- 성공 문구는 결과 중심으로, 실패 문구는 원인 중심으로 정리
- 조회 결과는 목록형/상태형/상세형으로 일관된 표현 사용

완료 기준:
- 응답이 전체적으로 하나의 assistant가 말하는 것처럼 느껴진다.

### 6. 사용자 시나리오 기반 대화 QA 세트 구축

필수 작업:
- 자주 쓰는 자연어 패턴 모음 작성
- 축약어, 정정, 취소, 재승인, 연속 요청을 포함한 QA 세트 작성
- 이 시나리오를 자동/수동 테스트 기준으로 사용

완료 기준:
- 기능 단위 테스트가 아니라 실제 대화 시나리오 기준으로 품질을 판단할 수 있다.

## 구현 순서

### 1순위

- 자연어 승인/거절
- 다중 턴 값 정정
- entity memory 기반 문맥 해석 강화

### 2순위

- 자연어 파라미터 추출 고도화
- 질문/결과 문구 정리
- 조회 응답 포맷 개선

### 3순위

- 대화 QA 세트 구축
- 실제 사용자 표현 기준 회귀 검증

## 완료 기준

다음 조건을 모두 만족하면 사용자 UX 100%로 본다.

- 사용자가 자연어만으로 요청, 보완, 승인, 취소를 끝낼 수 있다.
- 내부 상태, 내부 API 이름, 내부 ID를 보지 않는다.
- 여러 턴 대화에서도 대상과 값이 안정적으로 이어진다.
- 잘못된 값이나 애매한 표현은 안전하게 재질문한다.
- 응답 톤과 구조가 일관되어 실제 LLM처럼 느껴진다.
